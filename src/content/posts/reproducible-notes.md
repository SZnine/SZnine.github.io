> [!NOTE] 示例文章
> 这是一篇可替换的示例文章。下文使用假设的“请求超时”问题说明记录方式，不包含真实生产环境或已验证的性能结论。

## 从现象和预期开始

一份技术记录首先要让后来的人知道：当时正在做什么，实际看到了什么，希望发生什么。假设一次请求返回超时，就需要记录触发动作、错误文本、发生范围，以及预期的正常响应。先写能观察到的事实，再写可能原因。

“接口不稳定”很难用于复现。把它拆成具体请求、输入条件和返回结果，才有机会找到相同条件下的重复现象。如果目前只遇到一次，也要明确写出，避免把偶发现象当成确定规律。

## 给环境留下一个快照

| 记录项 | 应该保存什么 | 为什么需要 |
| --- | --- | --- |
| 版本 | 提交号、依赖版本、运行时版本 | 找到当时运行的代码 |
| 配置 | 与问题相关的选项 | 对齐触发条件 |
| 输入 | 可公开的最小样本 | 重新执行同一任务 |
| 证据 | 日志片段、截图或输出文件 | 检查判断是否成立 |

这里只需要与问题有关的信息。配置可以保留字段和有效选项，凭证等内容使用明确的占位符；样本经过替换后，也要说明哪些条件被保留、哪些条件已经变化。

## 每次尝试只回答一个问题

假设正在判断超时是否来自重试等待，可以先检查一次请求内部实际发生了几次调用。记录这次尝试的目的、修改项和观察结果；如果同时改动超时、并发和输入，就很难知道哪个变化起作用。

下面是一条格式示例，字段值只用于演示：

```json
{
  "case": "timeout-demo",
  "question": "是否发生重试",
  "change": "增加每次调用的开始与结束记录",
  "result": "待执行",
  "next": "对照调用次数与错误时间"
}
```

未执行的步骤应保持“待执行”。观察与预期不一致时，也应原样保留，这类结果经常能排除一个看似合理的解释。

## 把结论写到证据能够支持的位置

一次成功只能说明这次条件下成功了。如果想确认问题已经修复，就要重跑原先失败的样本，并说明检查范围。还没有覆盖的输入、网络条件或版本，留在“未验证”一栏，方便后续补充。

## 给下一次继续留一个入口

结尾保留三项信息就够用：当前判断、尚未解决的问题、下一个具体动作。附上相关文件和命令的位置，让下一次打开记录时可以接着做。技术记录的价值，也体现在减少重新理解上下文的时间。
