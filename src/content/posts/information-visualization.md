在自然语言转 KE、Agent 排错或项目评审中，读者通常带着一个具体问题进入页面：哪里不对，证据是什么，下一步查哪里。可视化的设计，应从这个阅读任务开始。

## 先确定读者要作出的判断

“展示运行过程”还不够具体。“让标注者发现原句与生成结果的语义差异”，才足以决定页面该放什么。

Munzner 的可视化设计模型依次讨论业务问题、数据与任务抽象、视觉编码和实现；上游判断错误，会传递到后面的设计。[¹](https://www.cs.ubc.ca/labs/imager/tr/2009/NestedModel/) 在挑选图表之前，先写清**读者、问题和判定依据**。

## 把一次语义错误摊开

用一个演示例子：

> 筛选片长**超过 120 分钟**，且评分**至少 8 分**的电影。

接口成功返回、语法检查通过，都不能说明原意被保留。假设候选结果把“超过”变成“至少”，一个全绿的执行流程图就会漏掉真正的问题。

先把双方翻译成同一种可比较结构，暂不涉及具体 KE 语法：

| 原句片段      | 预期条件           | 候选条件           |
| ------------- | ------------------ | ------------------ |
| 超过 120 分钟 | 片长 **>** 120 min | 片长 **≥** 120 min |
| 评分至少 8 分 | 评分 ≥ 8           | 评分 ≥ 8           |
| 且            | 两个条件同时满足   | 两个条件同时满足   |

差异收敛到了一个运算符。再放入“片长恰好 120 分钟、评分 8.5”的反例，就能看见它怎样改变结果。

![同一部片长 120 分钟、评分 8.5 的电影，按原句的严格大于条件应被排除，候选转换却用大于等于将它错误收录。](/images/engineering-notes/semantic-boundary.svg)

原句提供依据，条件对照定位偏差，反例验证影响。工程人员可以据此检查比较符映射，业务人员也能复核含义。

## 按问题选择表达形式

| 读者要做什么           | 优先展示                             |
| ---------------------- | ------------------------------------ |
| 比较版本或语义差异     | 对齐的表格，突出变化字段             |
| 找出谁阻塞谁           | 有方向的依赖图，标注阻塞原因         |
| 定位耗时               | 共用时间轴，区分执行与等待           |
| 判断一次改动有没有改善 | 相同样本的前后结果，以及失败类型变化 |

图的边也需要语义。“调用”“依赖”“由此推导”应分别标注；仅用一根箭头连起来，读者可能补上并不存在的关系。颜色之外保留状态文字，缺失信息明确显示为“未知”。

## 信息多了，先组织入口

Shneiderman 提出的信息查找原则是先看概览，再缩放、筛选，最后按需查看详情。[²](https://www.cs.umd.edu/~ben/papers/Shneiderman1996eyes.pdf) 落到工程界面，可以保留三层：

1. **概览**：当前对象、主要状态、失败类别。
2. **局部**：选中对象及其直接关联项，保留过滤条件。
3. **证据**：原句、输出、规则版本和运行记录，并提供返回入口。

大图放不下时，优先聚合、切片或切换列表。不要靠不断缩小字体，把阅读负担交给使用者。

做完后，找一个没参与开发的人，给他一条失败样本：他能否指出问题位置、找到依据，并返回上一步继续查？记录误判、求助和来回跳转的位置，再改那一处表达。
