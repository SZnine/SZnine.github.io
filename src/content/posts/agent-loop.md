## 先把任务写具体

假设任务是：读取指定目录中的 Markdown 文档，生成一份包含标题、路径和简短说明的索引。开始之前，需要确定允许读取的目录、输出文件的位置，以及什么情况算完成。这样才能判断一次工具调用是否服务于目标。

“整理一下资料”还不够明确。可以补充为：只处理当前目录中的文档，保留原文件，无法读取的文件列入异常清单。范围与例外写清楚，后面的动作才有依据。

## 四个相互衔接的步骤

| 步骤 | 要解决的问题 | 留下的记录 |
| --- | --- | --- |
| 判断 | 当前还缺什么信息？ | 下一步动作及原因 |
| 调用 | 哪个工具能取得这些信息？ | 工具名称与参数 |
| 观察 | 实际返回了什么？ | 结果、错误或缺失项 |
| 更新 | 是否需要继续？ | 当前进度与停止原因 |

工具返回后，需要把观察加入状态。目录为空、文件不存在、文本无法解析，都可能改变下一步选择。模型不能仅凭先前的计划，就认定这些动作已经成功。

## 把循环和边界写在程序里

下面是控制流程的伪代码，`decide` 与 `call_tool` 需要由具体实现提供：

```python
state = {"goal": goal, "observations": []}

for step in range(max_steps):
    action = decide(state)
    if action["type"] == "finish":
        break
    result = call_tool(action)
    state["observations"].append(result)
else:
    state["stop_reason"] = "step_limit"
```

真实实现还需要检查工具名称、参数范围和异常结果。最大步数只是最后一道限制；连续出现相同错误时，也应该停止或改变方案，避免重复执行没有进展的动作。

## 完成需要有证据

文档索引任务可以用几项可观察结果验收：扫描到了哪些文件、生成了哪个索引、哪些文件未被处理，以及输出中的链接是否有效。最终说明应能指向这些结果，而不是只有一句“已经完成”。

失败时同样要保留进度。已经处理的文件和失败位置可用于下一次继续，错误信息则帮助判断是输入问题、工具问题，还是决策需要调整。

## 第一次实现时关注什么

先让一个范围明确的任务完整跑通，再检查每一步能否解释、错误能否定位、结束条件能否验证。等这条执行链稳定之后，再考虑更多工具、并行处理或多 Agent 分工。新增能力应当对应已经遇到的具体问题。
