把“片长超过 120 分钟”转换成 `duration_min >= 120`，解析器可能照常通过，结果却多收了一类电影。演示顺利，仍然回答不了：这种错误出现在哪些输入上，改版后有没有减少？

**评测集把“做对”写成可重复检查的样本；开发流程决定每次投入之前，需要拿到什么证据。**

## 先把目标写成可检查的样本

先从真实任务、历史错误和边界条件取样，按任务与风险分组。以下以只支持**只读影片查询**的转换系统为例：

| 类型     | 输入或场景                          | 应检查什么                           |
| -------- | ----------------------------------- | ------------------------------------ |
| 正常     | 找出片长超过 120 分钟的电影         | 电影范围、分钟单位、严格大于均被保留 |
| 边界     | 用上面的条件检查恰好 120 分钟的电影 | 不入选；换成 121 分钟才入选          |
| 未知单位 | 找出片长超过 120 格的电影           | 指出单位未知，暂不生成可执行条件     |
| 歧义     | 找出比较长的电影                    | 没有约定阈值时先追问                 |
| 超出范围 | 删除不符合条件的电影                | 不执行删除，说明当前仅支持查询       |

每条样本至少保存：**输入、允许的上下文与本体版本、期望行为、评分规则、来源和标注版本。** 有争议的答案先澄清规则，再纳入验收。

评测集也会暴露需求缺口：“比较长”是否已有业务定义？单位缺失时能否默认分钟？这些约定应先写进任务边界。

## 分层测，才知道改哪里

对自然语言转 KE，可以分别记录：

- **语法通过率**：解析器是否接受。
- **语义正确率**：概念、关系、否定、量词、比较边界和单位是否保留。
- **任务成功率**：完整流程是否交付正确结果。
- **运行代价**：时延、调用成本及人工修正量。

每项都要固定分母和失败定义，避免把“通过解析的样本中有多少正确”误写成整体正确率。固定模型、提示词、本体和工具版本；对随机输出重复运行并报告波动。

同一语义可能有不同 KE 写法。评分应检查规范化结构、关键约束和[边界反例](/posts/information-visualization/)；只在一份数据上得到相同结果，也不足以证明两个表达式语义等价。无法自动判断的部分由人工复核，模型裁判则先用人工样本校准。

调提示词、规则和模型时使用**调试集**；另留独立样本作验收。同源模板及其近似改写应放在同一分组。将数据划分的原则用于这类系统，关键是防止依据验收结果反复调优，逐渐失去独立检验的意义。[¹](https://developers.google.com/machine-learning/crash-course/overfitting/dividing-datasets)

> 小样本适合早期找错。报告各类通过数量和失败案例；几次全对，还不足以证明系统可靠。

## PoC 要交付什么？

可以按要回答的问题，区分几种常见做法：

| 做法                  | 要回答的问题               | 主要证据                       |
| --------------------- | -------------------------- | ------------------------------ |
| **PoC：概念验证**     | 关键技术假设能成立吗？     | 对照实验、适用边界、失败条件   |
| **原型**              | 用户能理解并完成操作吗？   | 实际任务中的操作与反馈         |
| **MVP：最小可行产品** | 最小功能能产生真实价值吗？ | 一个可使用的业务闭环及使用反馈 |
| **试点**              | 在真实约束下能稳定运行吗？ | 有限范围的运行结果与退出方案   |

它们可以并行、合并，并非每个项目都要逐项打卡。先验证最可能让项目失败的假设，是 GOV.UK Alpha 指南强调的方法。[²](https://www.gov.uk/service-manual/agile-delivery/how-the-alpha-phase-works)

例如，NL→KE 的 PoC 可以只回答：**加入术语约束和结构校验后，比较边界错误是否比基线减少？** 开始前就写明样本、判据、资源上限，以及不达标时是换方案、缩范围还是停止。结果应足以支持下一次决策。

## 工程开发的共同骨架

工程通常要明确需求与验收、选择方案、实现与集成、验证与交付，再根据运行反馈修正。安全要求、法规约束和变更成本，会影响每一步的深度与顺序。

对这里的 AI 应用，可以用下面的反馈循环组织工作：

![任务与验收产生样本判据和高风险验证任务。调试与回归集用于实验和日常检查，独立验收集用于最终检验。证据支持后实现与集成，评测失败返回实现，通过后试点与运行，真实失败补入回归集。](/images/engineering-notes/engineering-evidence-loop.svg)

评测样本在需求阶段开始准备，每次改版跑回归。关键假设不成立，就调整范围或停止；试点检验真实流程，运行反馈再更新需求和样本。

上线前还要落实权限、日志、监控、回滚及责任人。NASA 分别检验“是否符合要求”与“在预定环境中是否满足使用目的”；规格达标和实际可用，都需要证据。[³](https://www.nasa.gov/reference/5-0-product-realization/)
